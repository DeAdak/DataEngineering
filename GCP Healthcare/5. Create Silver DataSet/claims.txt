## 1. Architecture & Design Patterns
## Question: Why did you use a UNION ALL with a NULL AS Merge_Key inside the USING clause? Why not a standard MERGE?

* The Answer: A standard MERGE statement can only execute a single clause per row. If a record matches on the primary key, it can only trigger the WHEN MATCHED update block to expire the old record. It cannot simultaneously insert the new, modified version of that record.
* By duplicating the changed records in a secondary virtual stream (UNION ALL) and masking their keys as NULL, we force BigQuery to treat them as unmatched rows, successfully driving both the historical update and the fresh record insertion in a single pass.

## Question: How do you handle Slowly Changing Dimensions (SCD) Type 2 in BigQuery? What are the tracking columns you look for?

* The Answer: We track records using an operational flag (is_current) combined with temporal audit points (insert_date and modified_date). In an ideal scenario, enterprise tables use explicit point-in-time intervals like start_timestamp and end_timestamp (defaulted to a maximum high-water mark like 9999-12-31) to let downstream Business Intelligence tools run historical time-travel queries smoothly.

------------------------------
## 2. BigQuery Engine Optimization & Performance
## Question: Why did you choose FARM_FINGERPRINT and TO_JSON_STRING for change detection instead of explicit inequality chains (source.col != target.col)?

* The Answer: This is a performance optimization. Chaining 20+ columns using OR statements requires the BigQuery query planner to evaluate multiple logical expression pathways for every single row.
* Instead, TO_JSON_STRING(STRUCT(...)) bundles the entire row state into a single text block, and FARM_FINGERPRINT hashes it into a compact 64-bit integer. Comparing two integers is significantly faster for the slot execution engine, which lowers CPU strain and minimizes query compute bills.
* You are using the inequality operator (<>). In SQL, if any column contains a NULL value, source.column <> target.column evaluates to UNKNOWN (not TRUE). The match will fail to trigger an update even if data has changed.

## Question: Is FARM_FINGERPRINT(TO_JSON_STRING(STRUCT(...))) null-safe? What happens if one of the fields in your payload is NULL?

* The Answer: Yes, it is completely null-safe. The STRUCT layer securely holds missing data states, and TO_JSON_STRING explicitly converts a missing field into a literal "FieldName":null string token. Because the null characters form part of the final text string, the hashing function handles it perfectly without throwing compilation errors or breaking inequality checks.

## Question: Why did you partition by insert_date and cluster by Claim_Key and is_current on the Silver table?

* The Answer: Partitioning divides the physical storage by time boundaries, allowing BigQuery to prune partitions and avoid full-table scans. Clustering sorts the rows within those partitions based on frequently joined lookup keys.
* During a MERGE operation, this setup allows BigQuery to pinpoint the exact blocks where is_current = TRUE rows reside, drastically cutting down the volume of bytes processed and accelerating join speeds.

------------------------------
## 3. Data Governance & Defensive Quality Controls
## Question: What is the difference between CAST and SAFE_CAST? Why is SAFE_CAST crucial in a Silver layer loader?

* The Answer: Standard CAST throws a runtime failure and crashes the entire execution pipeline if it runs into dirty data (e.g., trying to turn text like 'REJECTED' into a number).
* SAFE_CAST is defensive. If conversion fails, it quietly returns a NULL value instead of crashing. This prevents a single invalid source row from bringing down the entire corporate data ingestion pipeline.

## Question: What is a Quarantine pattern in data engineering, and how did you implement it here?

* The Answer: A quarantine pattern isolates dirty, malformed, or broken records without halting the pipeline.
* In this script, the CASE WHEN block checks for missing primary business attributes (ClaimID IS NULL, PatientID IS NULL) or explicit literal system string errors (LOWER(ClaimStatus) = 'null'). If caught, it sets is_quarantined = TRUE. This allows valid rows to flow cleanly to analytics tables while corrupted lines are kept out of active metrics but remain available for auditing.
